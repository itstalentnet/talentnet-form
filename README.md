تسک توسعه: TalentNet Form
در پروژه فعلی، یک سامانه پرسش‌نامه آنلاین فارسی و راست‌چین با نام TalentNet Form پیاده‌سازی کن. فایل پرسش‌ها، فونت‌ها و لوگوی TalentNet در پروژه قرار دارند؛ قبل از ساخت UI، ساختار پروژه و فایل‌های موجود را بررسی کن و از همان‌ها استفاده کن. پرسش‌ها و گزینه‌ها را بدون حذف یا تغییر معنا وارد کن.
هدف
فرم برای کارفرما ارسال می‌شود تا پرسش‌های نیازسنجی پروژه را مرحله‌به‌مرحله پاسخ دهد. پاسخ‌ها باید با هر مرحله ذخیره شوند، نسخه‌های قبلی باقی بمانند و من بتوانم نتیجه نهایی را از یک لینک خصوصی مشاهده کنم.
طراحی و تجربه کاربری
- رابط کاربری کاملاً فارسی، RTL و واکنش‌گرا برای موبایل، تبلت و دسکتاپ باشد.
- نام محصول TalentNet Form باشد و لوگوی موجود در پروژه در هدر نمایش داده شود.
- فونت عنوان‌ها از فونت مربع موجود در پروژه و فونت سؤال‌ها و متن‌ها از ایران‌سنس باشد.
- انتخاب تم روشن و تاریک در رابط وجود داشته باشد و انتخاب کاربر حفظ شود.
- فرم به بخش‌ها و مراحل کوتاه تقسیم شود؛ کاربر بتواند مرحله قبل را مرور و پاسخ‌ها را ویرایش کند.
- نوار پیشرفت، عنوان مرحله، تعداد مراحل باقی‌مانده و دکمه‌های واضح «مرحله قبل» و «ذخیره و ادامه» داشته باشد.
- انیمیشن‌ها نرم، کوتاه و کاربردی باشند؛ از افکت‌های مزاحم یا طولانی استفاده نشود.
- پاسخ تشریحی، انتخاب تکی، انتخاب چندگانه و سؤال‌های شرطی متناسب با نوع سؤال پشتیبانی شوند.
- امکان انتخاب «هنوز تصمیم‌گیری نشده» برای سؤال‌های مربوطه حفظ شود.
- برای حرکت بین مراحل، خطاها، ذخیره موفق و مشکل اتصال پیام روشن نمایش داده شود.
- فرم با کیبورد قابل استفاده باشد و برچسب‌ها، فوکوس و کنتراست مناسب داشته باشد.
- تغییر تم، رفرش صفحه یا بازگشت کاربر نباید پاسخ‌های ثبت‌نشده را از بین ببرد.
مسیرهای موردنیاز
- /form1 — فرم پاسخ‌گویی
- /form1/result — نمایش نتیجه فقط برای مدیر مجاز
هر فرم با یک شناسه یکتا ذخیره شود. لینک نتیجه نباید عمومی یا قابل حدس باشد. دسترسی به صفحه نتیجه را با احراز هویت امن مدیر، مانند رمز عبور مدیر یا سازوکار امن موجود در پروژه، محدود کن. مخفی‌کردن لینک به‌تنهایی احراز هویت محسوب نمی‌شود.
ذخیره‌سازی و نسخه‌بندی
برای این پروژه از دیتابیس استفاده نکن، مگر اینکه محدودیت فنی موجود در پروژه مانع اجرای مطمئن راهکار GitHub شود.
- پاسخ‌ها را در مخزن خصوصی GitHub داخل پوشه‌ای مشخص مانند data/forms/ ذخیره کن.
- از فایل‌سیستم محلی یا متغیرهای حافظه‌ای Vercel به‌عنوان ذخیره‌سازی دائمی استفاده نکن.
- تمام عملیات GitHub از API سمت سرور انجام شود.
- برای هر فرم یک فایل JSON اصلی شامل آخرین نسخه و فایل‌های جداگانه برای تاریخچه نسخه‌ها نگه دار؛ برای مثال:
  - data/forms/<form-id>/latest.json
  - data/forms/<form-id>/versions/<timestamp>-<revision>.json
- هنگام هر ذخیره تأییدشده، نسخه جدید ایجاد شود و نسخه‌های قبلی حذف یا بازنویسی نشوند.
- فایل آخرین نسخه باید همیشه آخرین پاسخ تأییدشده را نشان دهد.
- پاسخ‌ها شامل شناسه فرم، زمان ایجاد، زمان آخرین ذخیره، شماره نسخه و مقادیر پاسخ‌ها باشند.
- برای جلوگیری از ذخیره ناقص، ابتدا نسخه جدید با موفقیت در GitHub ثبت شود و فقط بعد از دریافت تأیید سرور به کاربر پیام «ذخیره شد» نمایش داده شود.
- اگر GitHub API خطا داد یا اتصال قطع شد، پاسخ‌های محلی موقت حفظ شوند، خطای واضح نمایش داده شود و امکان تلاش مجدد وجود داشته باشد.
- در صورت هم‌زمانی یا تعارض نسخه، داده قبلی بی‌صدا بازنویسی نشود؛ تعارض ثبت و مدیریت شود.
ذخیره خودکار و اطمینان از ثبت پاسخ‌ها
- پاسخ‌ها هنگام تغییر در مرورگر موقتاً ذخیره شوند تا با رفرش یا قطع اتصال از بین نروند.
- هنگام رفتن به مرحله بعد، پاسخ‌های همان مرحله به سرور ارسال و ذخیره شوند.
- ذخیره خودکار با تأخیر کوتاه پس از تغییر پاسخ نیز پیاده‌سازی شود تا ویرایش‌های کاربر ثبت شوند.
- رابط باید وضعیت هر ذخیره را نشان دهد: «در حال ذخیره»، «ذخیره شد»، یا «ذخیره ناموفق؛ تلاش مجدد».
- پیش از ثبت پاسخ جدید، اگر ذخیره قبلی ناموفق بوده، کاربر از ادامه بدون ذخیره مطلع شود.
- هنگام بازگشت به فرم موجود، آخرین نسخه ذخیره‌شده از سرور بازیابی شود و با ذخیره محلی تطبیق داده شود.
- در پایان، صفحه تأیید ارسال نهایی نمایش داده شود و شناسه یا کد پیگیری فرم به کاربر نشان داده شود.
تنظیمات محیطی و امنیت
این متغیرها را در مستندات پروژه معرفی کن و مقادیر واقعی را در کد یا مخزن قرار نده:
GITHUB_TOKEN=
GITHUB_OWNER=
GITHUB_REPO=
GITHUB_BRANCH=
ADMIN_ACCESS_SECRET=

- GITHUB_TOKEN باید فقط در Environment Variables سمت سرور در Vercel تنظیم شود؛ هرگز از متغیرهای عمومی فرانت‌اند مثل NEXT_PUBLIC_* استفاده نشود.
- توکن فقط حداقل مجوز لازم برای نوشتن در مخزن خصوصی مربوطه را داشته باشد.
- مقادیر ورودی سمت سرور اعتبارسنجی شوند؛ شناسه فایل یا مسیر ذخیره‌سازی از ورودی کاربر پذیرفته نشود.
- برای فرم عمومی، محدودیت نرخ درخواست و محافظت پایه در برابر ارسال خودکار هرزنامه اضافه شود.
- خطاهای داخلی، توکن‌ها و جزئیات پاسخ GitHub به کاربر افشا نشوند.
- در این پرسش‌نامه اطلاعات واقعی مراجعان، تشخیص‌ها، سوابق درمانی یا داده شخصی حساس درخواست یا ذخیره نشود.
- صفحه نتیجه و API دریافت پاسخ، بدون احراز هویت مدیر اطلاعات فرم را برنگردانند.
تست‌های پذیرش الزامی
پیش از تحویل، موارد زیر را در محیط محلی و Preview استقرار Vercel تست و نتیجه را ثبت کن:
1. پاسخ چند مرحله وارد و ذخیره شود؛ صفحه رفرش شود؛ آخرین پاسخ‌ها بازیابی شوند.
2. پاسخ در مرحله اول ذخیره شود، سپس چند جواب در مراحل بعد ویرایش شود؛ آخرین نسخه همه ویرایش‌ها را داشته باشد.
3. هر بار ذخیره تأییدشده، یک نسخه تاریخی جدید بسازد و نسخه قبلی همچنان قابل بازیابی بماند.
4. پاسخ نهایی از /form1/result برای مدیر مجاز نمایش داده شود.
5. کاربر بدون مجوز نتواند نتیجه را ببیند یا از API دریافت کند.
6. با تنظیم توکن نامعتبر یا شبیه‌سازی خطای GitHub، فرم پاسخ‌ها را پاک نکند و وضعیت ذخیره ناموفق و امکان تلاش مجدد را نشان دهد.
7. کلید GitHub در فایل‌های خروجی مرورگر، Network payload یا سورس عمومی قابل مشاهده نباشد.
8. فرم در اندازه‌های موبایل و دسکتاپ، RTL، هر دو تم روشن و تاریک، و حالت خطا بررسی شود.
9. ارسال دوباره یک درخواست باعث ایجاد فایل ناقص یا از دست‌رفتن آخرین پاسخ نشود.
10. در پایان، دستورالعمل تنظیم متغیرهای محیطی Vercel و روش مشاهده و حذف دستی فایل پاسخ‌ها از مخزن خصوصی نوشته شود.
نکته اجرایی
این روش برای فرم نیازسنجی کم‌تعداد قابل اجراست و روی Vercel هم کار می‌کند، چون Vercel میزبان رابط و API است و GitHub محل ذخیره دائمی خواهد بود. اما چون هر ذخیره، تغییر جدیدی در تاریخچه Git ایجاد می‌کند، API نباید با هر ضربه کلید commit بزند؛ ذخیره مرحله‌ای و خودکار با تأخیر کوتاه مناسب‌تر است. همچنین فایل‌های حذف‌شده ممکن است همچنان در تاریخچه Git باقی بمانند؛ اگر حذف کامل پاسخ بعد از بررسی لازم است، دستورالعمل پاک‌سازی تاریخچه یا حذف امن مخزن/شاخه نیز باید مشخص شود.
توجه: این نسخه‌بندی پاسخ‌ها به معنی ثبت snapshot در هر ذخیره تأییدشده است، نه نگهداری تک‌تک ضربه‌های کیبورد. این هم تجربه را روان‌تر می‌کند و هم از ساختن تعداد بسیار زیاد commit جلوگیری می‌کند.
